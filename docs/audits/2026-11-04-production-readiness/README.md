## Product and acceptance boundary

[Verified] Filing Agent is a single-owner local filing investigation application and a public static replay. The intended reader asks Korean or English follow-up questions, inspects source-bound figures, compares compatible annual periods, and preserves saved investigations. The public service shows selected authentic recordings; it does not accept live visitor questions or connect to the owner's Mac. This audit retains the maintenance boundary in `docs/MAINTENANCE.md`, the historical fifteen-figure collection, pinned Gemma/Ollama configuration, Decimal financial policy, frozen saved evidence and explicit recovery semantics.

[Verified] Initial repository HEAD was `f71c0546ca2463c6ffada21169ae50068aefdd9d`, with a clean worktree. A task branch preserved unrelated processes and partner-project edits. Tests used a disposable PostgreSQL 16 cluster/database on port 55440. The existing service on port 8765 and user's PostgreSQL service were untouched. An alternate loopback app on port 8767 used a test-only adapter translating its exact Host/Origin to the canonical app origin; unrelated/hostile values remained rejected.

Success criteria established before implementation: reproduce consequential defects; preserve financial/ownership/recovery invariants; meaningful red/green regressions; real PostgreSQL transaction/recovery checks; actual connected app/model/DB workflows; rendered desktop/mobile, both languages/themes, keyboard/text scaling/reduced motion; independently review frozen commits; protect public artifact boundaries; merge required-green PR; deploy only the reviewed hash manifest; verify production bytes and browser behavior; retain rollback.

## Findings and fixes

[Verified] Findings below were reproduced before their fixes. P2 denotes a material local workflow, privacy or accessibility defect; P3 denotes avoidable work with a bounded operational effect. Registry advisory severities are reported separately.

| ID | Severity and affected surface | Evidence and correction |
|---|---|---|
| F01 | P2 local API resource boundary | Declared Content-Length alone allowed chunked/false-length bodies past 8,192 bytes and malformed headers raised exceptions. A narrow pure-ASGI boundary now checks declarations and actual streamed bytes, rejects before reading when possible, stops on overflow and faithfully replays bounded valid JSON. Exact Host/Origin/Fetch Metadata/token checks remain first. |
| F02 | P2 durable enqueue recovery | A lost initial commit acknowledgement orphaned queued work. Recovery retains a conservative interrupted attempt, reconciles either committed or rolled-back queue writes without inference, and requires explicit retry/discard. |
| F03 | P2 duplicate execution | Two submissions could both read an absent request before serialized append. Identity is checked inside the row-locked mutation and returned with dispatch ownership, preventing a second append/inference. |
| F04 | P2 local runtime lifecycle | Worker EOF/read failure bypassed upstream stop confirmation. Started clients are reaped and stop is confirmed; surviving clients remain tracked and block new inference. Pre-start failures close pipes without unloading unrelated inference. |
| F05 | P2 diagnostic privacy | Cache could serve expired raw output or overwrite durable deletion during storage retry. Cached reads/persistence sanitize expired output, manual clearing writes a per-turn deletion marker, and persistence preserves it under row lock. Unverifiable cached raw output is hidden. |
| F06 | P2 execution dispatch, independent-review finding | Thread construction/start failure left a phantom event and stranded queue. Dispatch failure now removes its event and durably records interruption, retaining explicit storage recovery if that receipt fails. |
| F07 | P2 diagnostic retention, independent-review finding | Retrying copied raw output into a new capture timestamp and extended retention. Reused intent/results/metadata remain; raw output is no longer copied to retry turns. |
| F08 | P2 mobile accessibility | Live Korean controls overflowed a 320px viewport (document width 338–340px). Retain all direct controls and brand, with deliberate header rows within the available width. |
| F09 | P2 reading continuity | Rapid 390→851→390px breakpoint reversal moved evidence scroll from 120 to 158px. Disable browser scroll anchoring on the moving mobile evidence reader, preserving 120px without weakening the regression. |
| F10 | P2 recording error recovery | Reload recording from the failed Recorded runs view returned to Overview. Preserve the recording destination before reload and capture Home card selection before a pending or failed recording can drop it. Require actual re-requests and correct scenario recovery in the tests. |
| F11 | P2 text scaling | At 200% text, a 320px replay expanded to 396px, the source badge overlapped the amount, and English scenario choices overlapped. The coverage table and Ledger also overflowed at enlarged text sizes, and light-theme token specificity masked responsive settings. Fix shared responsive tokens, retain whole Korean words, and use named keyboard-scrollable regions for data. Body font size and native table semantics remain unchanged; header controls, chart labels and scenarios adapt to available space. |

| F13 | P2 verification reliability | Documented browser checks still targeted superseded selectors, controls and entry screens. Cache only generated content-hashed assets for one year; retain HTML/JSON/ZIP revalidation and global security headers. Production readback remains a release gate. |

## Residual risks

- Independent financial/semantic evaluation, physical-device accessibility and full VoiceOver remain outside the established evidence.
- A small fixed historical catalog and single-owner loopback deployment are intentional product limits, not a multi-user production-service readiness claim.
- Memory-only unsaved results are not durable across process shutdown; explicit backups can reintroduce previously deleted data. The interface and operating guide retain these boundaries.
- Static hosting success is not application-model/DB production operations; local connected evidence and public replay evidence are reported separately.
